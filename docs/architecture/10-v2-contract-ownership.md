# V2 Contract Ownership

This page records the current contract ownership boundary after Storefront V2 moved away from `Web.SharedV2` as a business DTO bucket.

## Rules

- Public HTTP contracts live at the API boundary that exposes them.
- Commerce Node Storefront public HTTP contracts are canonical at the `api/storefront/stores/{storeKey}/*` boundary.
- Generated Storefront clients are frontend-readable contracts and must be regenerated from the canonical Storefront OpenAPI contract at `contracts/storefront/storefront.openapi.json` instead of hand-copied into frontend packages.
- Storefront frontend view models are allowed when they are presentation or composition models.
- Storefront frontend code must not add handwritten duplicate API DTO clones when the schema should come from OpenAPI-generated contracts.
- Storefront browser/local endpoint contracts live in `BlazorShop.Storefront.Presentation/Endpoints/Contracts` or `BlazorShop.Storefront.Presentation/Services/Contracts` when the contract is shared by Presentation route/BFF/page services. A host may own a narrower local extension only when it is documented and not duplicated by Presentation.
- Storefront component contracts are presentation contracts, not public HTTP API contracts. Use `BlazorShop.Storefront.Components/Contracts/*` for stable render/input models and `Headless/*` for browser-safe state/behavior contracts. Same-origin browser transport, request DTO construction, mutation state, JS interop assets, and cart/checkout/account controllers belong in `BlazorShop.Storefront.Browser`. Store-specific visual templates are host-owned; Storefront V2 interactive root components that hydrate in the browser live in its WASM client assembly and delegate to Browser controllers.
- Cart and checkout class/label contracts live in `Components/Contracts/Cart` and `Components/Contracts/Checkout`: `StorefrontCartViewClasses`, `StorefrontCartViewLabels`, `StorefrontCheckoutViewClasses`, and `StorefrontCheckoutViewLabels`. WasmHost implementations receive those neutral contracts; V2.WASM wrapper options own their final V2 copy and class values, while V2 pages own render-mode placement and the visible checkout form.
- Account leaf class/label contracts live in `Components/Contracts/Account`: form, address-book, order-list, order-detail class bags and neutral profile/password/address/order label bags. The five reusable leaves in `Components.WasmHost/Components/Account` use `IStorefrontBrowserAccountController`; `StorefrontAccountApp`, `StorefrontAccountNavigation`, and `StorefrontAccountViewOptions` retain V2.WASM composition and final V2 copy/classes. These are render/runtime contracts, never Presentation transport contracts or direct Commerce Node access.
- `BlazorShop.Storefront.Components.Primitives` may render reusable browser-safe Razor primitives over component contracts. It references `BlazorShop.Storefront.Components` only, is not a component mode, and must not own descriptors, final V2 classes/copy/layout, CSS/assets, Browser controllers, Presentation services, Runtime/Client access, backend/core/API references, or direct API calls.
- Navigation render contracts follow the same boundary: `StorefrontPaginationItem`, `StorefrontPaginationClasses`, and `StorefrontPaginationLabels` live in `Components/Contracts/Navigation`; the Primitive consumes already-prepared `Href` values only. `StorefrontCatalogFilterPanel`, `StorefrontBreadcrumb`, and `StorefrontConsentPanel` live in `Components.Ssr`, consume prepared Presentation contexts, and never construct host routes or own final V2 copy/classes. Presentation owns consent transport/state; the V2 wrapper retains registration, final values, and placement.
- Storefront component descriptors live in `BlazorShop.Storefront.Components/Contracts/Components` and describe semantic component mode/category/type metadata only. They are not a component registry, scanner, manifest engine, routing surface, or HTTP API contract.
- Reusable Storefront component mode libraries currently exist as `BlazorShop.Storefront.Components.Ssr` and `BlazorShop.Storefront.Components.WasmHost`. Their descriptors describe semantic render/runtime classification only. `Ssr` means server/static/prerender-capable surfaces; `Hybrid` means server-produced or prerendered HTML/page snapshots plus client-side WebAssembly interactivity after hydration; `WasmHost` means browser-side WebAssembly interactive roots that use Browser controllers. H1 removed descriptor/project ownership coupling. H2 proved that semantic `Hybrid` components may physically live in the downloadable WasmHost graph through `StorefrontHybridRuntimeProbe`; H3 retired the old physical `Components.Hybrid` compatibility project after moving the contact descriptor into WasmHost.
- Reusable component libraries may expose semantic hooks and host-supplied class slots, but they must not own V2 theme classes, theme CSS/assets, store-specific copy, generated storefront output, or direct Commerce Node routes. The detailed mode dependency graph and allowlists live in `BlazorShop.PresentationV2/COMPONENT-MODES.md`.
- Storefront Presentation owns shared page contexts, shell contexts, form contexts, local mutation contracts, route/action descriptors, selected product option state, SEO/status contexts, and BFF request/response contracts. Storefront V2, Starter, and generated storefronts render those contracts and submit to the supplied same-origin actions.
- Cart, checkout, and account browser action descriptors are Presentation page-context contracts. `StorefrontCartViewOptions`, `StorefrontCheckoutShellOptions`, and `StorefrontAccountViewOptions` are visual-only option bags; they must not contain hardcoded `/api/*` routes, navigation items, route descriptors, or default action descriptors with live endpoints.
- Storefront Presentation public namespaces use `BlazorShop.Storefront.Presentation.Services`, `BlazorShop.Storefront.Presentation.Contracts`, `BlazorShop.Storefront.Presentation.Models`, `BlazorShop.Storefront.Presentation.Options`, and `BlazorShop.Storefront.Presentation.Configuration`. Do not add new shared Presentation contracts under generic `BlazorShop.Storefront.Services`, `BlazorShop.Storefront.Models`, `BlazorShop.Storefront.Options`, or `BlazorShop.Storefront.Configuration` namespaces.
- Storefront V2 is a visual host only. Its server project must not directly reference `BlazorShop.Storefront.Runtime` or `BlazorShop.Storefront.Client`, inject `IStorefront*` application services, define shared contracts, or own BFF/manual mutation DTOs.
- Storefront V2 source must not import `BlazorShop.Web.SharedV2`/`Web.SharedV2` or backend/core business namespaces.
- Storefront Starter and generated storefront source must not import `BlazorShop.Web.SharedV2`/`Web.SharedV2` or backend/core business namespaces.
- Storefront Starter must use `AddStorefrontApplication()`, `UseStorefrontApplication()`, and `MapStorefrontApplication()` plus Starter view registrations only. It must consume generated Storefront client contracts through Runtime/Presentation by default and must not copy the manual `StorefrontApiClient` transport from Storefront V2.
- Generated StorefrontBuilder projects must consume `BlazorShop.Storefront.Presentation` and `BlazorShop.Storefront.Components` through package boundaries. Presentation exposes Runtime as the application dependency, and Runtime owns the direct `BlazorShop.Storefront.Client` generated transport dependency. Generated projects keep Client/Runtime package metadata for compatibility proof but must not directly compile against Runtime or Client types unless a documented low-level transport extension explicitly reopens that boundary. They must not reference Storefront V2, `BlazorShop.Web.SharedV2`, or backend/core/API projects.
- Storefront Runtime is server/BFF-only. Server hosts use `AddStorefrontPlatformRuntime` for the full surface or explicit `AddStorefront{Capability}Runtime` methods for narrow composition; compatibility aliases such as `AddStorefrontServerGeneratedClients` and `AddStorefrontGeneratedClients` are not part of the current API surface. Browser/WASM code uses same-origin local endpoints through `BlazorShop.Storefront.Browser` and browser-safe Components contracts/headless primitives instead.
- Starter manual HTTP exceptions are allowed only when documented in an exception registry with reason, owner, test, and revisit trigger.
- The Starter generated-client adoption policy and exception registry live under `docs/storefront-platform/`.
- `Web.SharedV2` may keep browser helpers and transitional model folders during migration, but new business model folders are not allowed.
- `Web.SharedV2` is currently a transitional Control Plane/shared browser-helper bucket. Storefront source must not reuse Control Plane auth/token/JWT helpers from it.
- Do not add Storefront-specific files, namespaces, route helpers, cookie names, or business models to `Web.SharedV2`; Storefront contracts belong in Storefront V2 local contracts, `Storefront.Client`, `Storefront.Runtime`, or `Storefront.Components`.
- If Control Plane Web becomes the only active consumer of `Web.SharedV2`, a later phase should merge the remaining helpers into `BlazorShop.ControlPlane.Web` or extract a small generic helper package only after at least two active consumers need it.
- Generated Storefront clients should target Commerce Node Storefront OpenAPI first. Control Plane generation is a later decision.

## Current `Web.SharedV2/Models` Inventory

| Folder/file group | Current consumers | Classification | Migration direction |
| --- | --- | --- | --- |
| `Models/Authentication` | Control Plane Web imports, legacy shared auth helpers, Storefront auth forms through Application DTOs | Transitional shared auth DTOs | Keep frozen until Control Plane auth contracts are split; do not add Storefront-only auth models here. |
| `Models/Category` | Storefront catalog pages/SEO, Control Plane compatibility tests and legacy-style admin models | Mixed Storefront + Control Plane | Move Storefront read models to generated Storefront client or Storefront V2 contracts; keep admin mutations out of Storefront contracts. |
| `Models/Product` | Storefront catalog/product/search pages, structured data, tests, Control Plane compatibility paths | Mixed Storefront + Control Plane | Storefront product read models should be generated from Storefront OpenAPI; admin create/update models belong to Control Plane/API contracts. |
| `Models/Discovery` | Storefront sitemap/discovery services and tests | Storefront-only | Candidate for Storefront V2 contracts or generated Storefront client. |
| `Models/Pages` | Storefront pages and SEO composition | Storefront-only | Candidate for Storefront V2 contracts or generated Storefront client. |
| `Models/Payment` | Storefront payment/order pages, historical/admin-compatible payment DTOs | Mixed Storefront order/payment + admin shipping/tracking | Split Storefront order/payment responses to generated Storefront client; admin shipping/tracking requests belong behind Control Plane contracts. |
| `Models/Seo` | Storefront SEO composition and Control Plane SEO admin flows | Mixed Storefront + Control Plane | Storefront SEO reads should move to Storefront contracts/generated client; SEO admin mutations belong to Control Plane/API contracts. |
| Root model files (`PagedResult`, `QueryResult`, `ServiceResponse*`, `ApiCall`, `Unit`, `LoginResponse`, `ToastModel`) | Shared browser helpers, Control Plane Web, some Storefront service contracts | Shared utility/transitional | Keep only genuinely shared primitives; do not add business models at root. |

## Existing Storefront V2 Contracts

`BlazorShop.Storefront.Presentation` already owns shared Storefront-local contracts for:

- Address lookup.
- Cart and product-selection preview.
- Checkout browser state and checkout commands.
- Consent.
- Current store/configuration/currency.
- Customer account, addresses, and orders.
- Payment attempts/methods.
- SEO, sitemap, pages, catalog, and rendering helpers.

`BlazorShop.PresentationV2/BlazorShop.Storefront.Client` is the generated Storefront HTTP client package. It is generated from the canonical committed Storefront contract at `contracts/storefront/storefront.openapi.json`, not from test snapshots, and must not reference backend/core/API projects or `Storefront.V2`. Test snapshots remain breaking-change guardrails only. Storefront V2 should consume this generated client through Runtime/Presentation instead of adding handwritten API DTO clones or direct host-view usage.

Generated StorefrontBuilder projects are not contract owners. They are disposable artifacts under ignored generated output roots, consume Storefront Presentation/Components packages directly, hold generated visual output, and keep review artifacts under their local `docs/storefront-analysis/`. Runtime remains a transitive Presentation dependency, and Client remains the generated API transport package owned by Runtime.

Generated storefronts must not infer Storefront API envelopes or field names from screenshots, examples, component models, or `Storefront.Components` render contracts. Server-side Runtime facades map typed generated client envelopes into Presentation/host-facing runtime results; browser components consume Presentation BFF contracts, documented host-local extensions, or `Storefront.Components` presentation/headless contracts.

## Portable Component Models And Headless Contracts

`BlazorShop.Storefront.Components/Contracts/*` is the preferred home for small render-facing models such as product summary cards, product gallery items/classes/labels, Product Detail display class/label contracts, and purchase panel snapshots after the headless presentation refactor.

`BlazorShop.Storefront.Components/Headless/*` is the preferred home for browser-safe presentation state and action/event contracts that can be reused without Storefront V2 visual markup. `BlazorShop.Storefront.Browser` is the preferred home for browser-side controllers that execute same-origin local API calls, own request DTO creation, normalize network/timeout/invalid-response failures, and provide Browser static web assets required by those controllers.

`BlazorShop.Storefront.Components.Primitives/*` is the approved location for narrow render-only Razor primitives when there is evidence of real reuse across host contexts. Product Summary primitives live there and consume `ProductSummaryItem`, `ProductSummaryLabels`, and `ProductSummaryCardClasses`; Product Detail gallery rendering lives there as `StorefrontProductGallery` and consumes `ProductGalleryItem`, `ProductGalleryLabels`, `ProductGalleryClasses`, and `ProductGalleryState`; `StorefrontProductPurchasePanel` consumes prepared purchase contracts plus `ProductPurchaseLabels`/`ProductPurchasePanelClasses`; and `StorefrontToastRegion` consumes `StorefrontToastRegionLabels`/`StorefrontToastRegionClasses`. The named Phase 3.4 extraction is an explicit architecture-approved preparatory reuse exception: V2 is its first host, and its neutral contracts remain consumable by Starter or generated hosts without copying V2 markup. Neutral host-supplied class slots are permitted, but final class values and copy are forbidden. V2 and V2.WASM still own final labels/classes, V2 owns Product Detail progressive-enhancement JavaScript, and V2 owns toast placement/CSS/visual behavior.

Navigation pagination is another approved primitive: `StorefrontPagination` consumes base `StorefrontPaginationItem`, `StorefrontPaginationClasses`, and `StorefrontPaginationLabels` contracts. Category and Search hosts prepare the route-specific `Href` values. `StorefrontCatalogFilterPanel` and `StorefrontBreadcrumb` are SSR references because they consume prepared Presentation form/breadcrumb contexts; the existing Presentation breadcrumb item remains the contract rather than being migrated without a browser-safe reuse need.

`BlazorShop.Storefront.Components.Ssr/*` is the approved location for reusable SSR display components over prepared Presentation views. Product Detail display components such as `StorefrontProductPricing`, `StorefrontProductAvailability`, and `StorefrontProductVariantList` consume `StorefrontProductPricingView`, `StorefrontProductAvailabilityView`, `StorefrontProductPurchaseView`, and `StorefrontProductVariantView`; `StorefrontConsentPanel` consumes the prepared `StorefrontConsentContext` and neutral labels/classes. Neither owns browser controllers, render modes, final V2 classes/copy, route descriptors, purchase payload behavior, or consent transport/state.

`BlazorShop.Storefront.Components/Features/*` was a temporary compatibility surface and is retired. Reintroducing shared visual Razor wrappers requires a new architecture decision; normal storefront implementation must keep route composition in Storefront Presentation and keep markup, CSS, layout, copy, and visual templates in V2 host/WASM client, Starter, or generated/custom storefronts.

These models are not public HTTP contracts. Storefront Presentation or a host maps API DTOs or local endpoint contracts into them before composition. They must not reference `Web.SharedV2`, `Application`, `Domain`, `Infrastructure`, Control Plane, Commerce Node runtime projects, Storefront API clients, or Storefront route helpers.

Do not add admin-owned fields, store ownership fields, credentials, tokens, passwords, server-owned publication flags, or cost/internal accounting fields to these component models.

Do not put V2 theme/layout classes, page containers, route strings, or hardcoded same-origin endpoint paths in reusable headless contracts. Host/storefront projects provide visual templates, while Storefront Presentation provides browser route/action descriptors through page contexts. WASM-owned interactive V2 components may consume those descriptors only after the V2 host supplies them.

Browser controllers are not app-wide snapshot owners. Initial cart, checkout, and account data can be passed from Presentation page contexts to avoid duplicate first-load fetches, but Browser controllers must rehydrate or reset state when the visible route, checkout session/cart version, or authenticated customer identity changes.

Product purchase selection state is a Presentation/storefront browser contract. Presentation maps raw product-selection preview responses into semantic event values such as `selection.priceText`, `selection.stockText`, `selection.skuText`, `selection.gtinText`, and `selection.mainImageUrl`. Storefront V2, Starter, and generated visual markup may render those values, but they must not inspect raw preview business fields or rebuild selection/add-to-cart payload contracts.

## Guardrails

- `V2ArchitectureBoundaryBaselineTests.WebSharedV2BusinessModelFolders_AreFrozenDuringContractMigration` freezes the allowed `Web.SharedV2/Models` folders.
- `StorefrontPageCompositionGuardrailTests.StorefrontComponentFeatures_DoNotDependOnBackendOrRouteContracts` keeps portable feature components presentation-only.
- `StorefrontPageCompositionGuardrailTests.StorefrontComponentFeatureModels_DoNotExposeAdminOwnedFields` blocks admin-owned/server-owned fields from component-facing models.
- `StorefrontEndpointDependencyBoundaryTests.StorefrontLocalEndpointMappings_DoNotInjectConcreteStorefrontApiClient` keeps endpoint mappings behind capability interfaces.
- `CommerceNodeStorefrontOpenApiContractTests.StorefrontSwagger_GeneratesAndCompilesTypeScriptClientWithNswag` proves Storefront OpenAPI remains generator-safe enough for non-.NET clients.
- `StorefrontGeneratedClientFoundationTests` proves the generated C# Storefront client compiles, uses generated-source guardrails, and has no backend/core project references.
- `scripts/qa/run-storefront-client-regeneration-gate.ps1` regenerates `BlazorShop.Storefront.Client` from the canonical contract and fails on generated-source drift before package release.
- `StorefrontVisualOnlyBoundaryTests`, `StorefrontPresentationFoundationBoundaryTests`, `StorefrontPresentationCutoverGuardrailTests`, `StorefrontStarterFoundationBoundaryTests`, and `StorefrontApplicationBootstrapTests` protect the final visual-only boundary and host-independent Presentation graph.
- StorefrontBuilder focused tests and `scripts/qa/run-storefront-builder-generated-proof.ps1 -ProofLevel Structure` prove generated storefronts keep package references, package compatibility metadata, generated artifacts, route uniqueness, browser/network guardrails, and forbidden dependency scans intact. PR closure uses `-ProofLevel FoundationFunctionalFast` to prove descriptor-driven browser action behavior through mocked same-origin Presentation BFF routes. Manual, scheduled, and release closure runs use `-ProofLevel FoundationFunctionalFull` to prove fixture-backed browser behavior.
